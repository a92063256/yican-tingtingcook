# 一键更新

Windows 用户双击根目录的 **`一键更新.cmd`**，英文入口 `update-lan.cmd` 功能相同。更新的是项目跟踪的远程分支中的程序与随版本提供的内容，包括内置菜谱、封面和来源信息。无需重新注册或重新创建厨房。

## 当前使用条件

- 使用 Git 拉取的完整项目，安装 Node.js 24+、npm、Git；Windows 自带的 `tar` 用于展开版本。源码部署仍需上述环境；免安装运行环境可使用 [Windows 便携版](Windows便携版使用说明.md)。当前没有一键开机自启。
- 当前分支配置了远程跟踪分支，更新器沿用该配置，支持 GitHub、Gitee 等 Git 远程，不写死网站或分支名。仓库发布新提交后才能获取；未提交、未推送的本机代码不会成为其他用户的更新。
- 首次获取版本和安装依赖需要联网。注册、厨房和菜谱浏览在部署完成后不依赖外部内容服务。
- 项目没有未提交修改、未跟踪的源码文件或与远程分叉的提交。遇到这些情况会说明原因并停止，不强制重置、不自动暂存、不覆盖本地工作。
- 源码 ZIP 不含 Git 版本信息，目前不能直接一键拉取新版。不要为更新重复解压覆盖使用数据。

## 使用流程

1. 日常通过 `start-lan.cmd` 启动部署版本，保留窗口。它现在包含启动管理器，便于更新器只停止和重启属于本项目的服务。
2. 需要更新时双击 `一键更新.cmd`，保留更新窗口直到成功或明确失败。下载和构建期间旧服务继续工作。
3. 更新器在独立目录安装依赖、构建，并在数据库副本上演练初始化；随后只在 `127.0.0.1` 启动新版预检。
4. 预检通过后，短暂停止受管理的服务，在 `data/backups/pre-update-*.sqlite` 保存一致性备份，准备真实数据库和新版内容。
5. 新版启动但暂不接受业务读写；确认就绪并持久保存切换结果后恢复访问，沿用原监听范围、端口和数据目录。手机刷新页面后使用新版，账号、库存、菜单、订单与私家做法保留。

更新只会继承已经运行的管理器配置，不自行开启新的局域网共享或放行防火墙。直接用 `npm start`、`npm run dev` 或其他方式启动的进程不会被结束；这时更新会准备并选定新版，下一次通过 `start-lan.cmd` 启动才生效，原进程仍使用旧代码。一个数据库同时只运行一份应用服务。

停服状态安装的版本会在下次受管理启动时再次备份最新数据库，在开放业务请求前完成首次启动检查；失败则恢复此前版本和启动前数据，不用安装时的旧备份覆盖这期间新增的数据。

没有新版时只提示已是最新；当前本机提交领先远程时提示无需更新。不会悄悄用远程旧版本覆盖本地新版。

## 数据和内容的更新边界

程序安装版本保存在 `.yican/releases`，`.yican/current.json` 记录当前选择。根目录保留启动入口和原 Git 检出，更新不通过重置根目录来替换代码；`npm run dev` 仍用于开发根目录源码，不用于运行选定的安装版本。以后新增的自启入口也应调用同一启动管理器。

同一版本重复运行更新不会重复安装。成功后保留当前和上一安装版本，清理更早的受管理程序目录，数据库备份与更新日志保留。更新时还需要放置候选版本及演练副本的空间，磁盘不足会导致准备失败，旧服务保留。

账号、会话和业务数据继续位于原 `data` 目录，或第一次启动指定的 `YICAN_DATA_DIR`。不会从远程覆盖数据库。内置菜谱随新版本进入初始化流程，按内容标记补充新增公共菜谱，不把全部菜谱自动加入已有菜单，也不覆盖既有私家做法和历史订单；当前内容更新规则见 [HowToCook 导入说明](HowToCook导入说明.md)。不会直接抓取 HowToCook 的最新主分支。

`.yican` 和 `data` 均不加入 Git。不要删除 `.yican` 来“清理更新缓存”，否则会丢失安装版本记录；不要手改其中的程序文件、控制凭据和事务记录。

## 失败与中断

- 下载、依赖安装、构建或副本演练失败：旧服务和真实数据库保持原样，修复网络等原因后重新双击即可。
- 切换阶段初始化或启动失败：新版未接受业务请求时，自动恢复旧版本及更新前数据库，再恢复原服务。失败后的数据库副本保留在 `.yican/recovery`。
- 更新进程意外关闭或断电：下次运行更新会识别未完成的切换并优先恢复；若上次准备进程仍在退出，会要求稍后重试，不结束未知进程。存在未完成切换时普通启动会阻止继续，提示先运行更新恢复。
- 一旦更新结果已提交并开放业务请求，就不会自动恢复旧数据库，避免抹去新版产生的使用数据。若此后服务异常，先查看状态和日志，再重新启动。

更新日志在 `.yican/logs/update-*.log`。诊断命令为 `node scripts/entry.mjs status`，停止受管理服务可用 `node scripts/entry.mjs stop`。管理通道是本机管道，不开放管理 HTTP 端口；不会根据“占用了某个端口”去结束其他程序。

## 验证与最小人工验收

自动验证使用隔离的 Git 仓库、数据库和本机服务，覆盖成功更新、无新版、端口与用户数据保留、构建失败、副本初始化失败、真实启动失败回退、源码修改／分叉拒绝、停止状态安装及首次启动失败恢复、中断恢复；另使用真实应用检查内置 369 道菜谱的准备及切换前写入阻止。

尚未对正式 GitHub／Gitee 发布进行端到端更新，也未验证真实手机 Wi-Fi、Windows 开机自启及断电。当前正式库没有执行更新或失败演练，未开放局域网或修改防火墙。

发布后若决定实机验收，最小范围是：在独立 Git 克隆与独立数据目录中启动一个旧版，用手机保存一笔订单；发布一个支持更新协议的新版本，双击更新，预期网址不变、刷新可见新版、原订单和账号保留。源码目录留一个未提交修改再更新，预期拒绝且修改不丢失。注意始终保留数据备份，开发验证可继续使用 `node scripts/entry.mjs start --host 127.0.0.1`，不必开放局域网。

## 从旧开发仓库切换到 GitHub

GitHub 正式仓库为 <https://github.com/a92063256/yican-tingtingcook>，以清理后的源码建立独立首次提交。旧开发仓库的历史继续保留，两者不共享提交祖先。

旧 Git 部署继续使用原远程时可按原链路更新。若切换到 GitHub，请先备份并停止旧服务，在新目录克隆正式仓库或解压新便携版，迁移完整的停止状态 `data` 目录后启动。不要对旧目录强制拉取、硬重置或强行合并无共同历史的分支。账号、厨房和库存由数据库保留，主题则按浏览器和网址保存。
