# 数据存储与餐后评价

## 当前保存位置

局域网共享版将数据持久化到项目的 `data/kitchen.sqlite`（设置 `YICAN_DATA_DIR` 可换目录）。手机通过 `/api/state` 读取同一份数据，提交业务命令后由服务器校验并保存。数据库与备份不加入 Git。

当前已采用 **SQLite 关系型业务表**。菜谱、食材、步骤、厨房成员、餐次、订单明细、库存和评价分别保存为行，主键、外键、唯一约束与查询索引由数据库执行。业务写入只更新变化的记录，网页通过版本号获取增量更新；不再重写整个应用 JSON。

完整表关系、索引、迁移校验、回退步骤和承载测试见 [关系型存储设计与迁移](关系型存储设计与迁移.md)。可执行建表定义在 `server/schema.sql`。`legacy_kitchen_state` 只是迁移时封存的旧快照，之后不更新，不能把它当作当前数据。

待提交的购物车保留在当前页面内存，刷新会清空；已提交订单进入 SQLite。评价草稿在当前页面中按身份、餐次、菜品分别保留，关闭评价抽屉或切换菜品不会清除，但刷新页面会丢失未保存草稿。体验身份在每个标签页的 sessionStorage 中保存。

非共享的 Vite 演示版将业务状态保存在浏览器 localStorage（`yican-vue-demo-v1`，QA 模式为 `yican-vue-demo-qa`），不与局域网数据库互相覆盖。

## 如何查看

共享服务运行时，可在本机浏览器打开 `http://127.0.0.1:3000/api/state` 查看 JSON。也可以在支持 SQLite 的查看器中以只读方式打开备份文件，执行：

```sql
SELECT revision, schema_version FROM app_meta;
SELECT id, name, category FROM recipe_versions ORDER BY sort_order;
SELECT o.id, m.date, m.name AS meal, u.display_name, r.name AS dish
FROM orders o
JOIN meals m ON m.id=o.meal_id
JOIN users u ON u.id=o.user_id
JOIN order_items i ON i.order_id=o.id
JOIN recipe_versions r ON r.id=i.recipe_id
ORDER BY m.date DESC, o.sort_order, i.position;
SELECT kitchen_id, name, amount, unit, type FROM inventory;
SELECT meal_id, recipe_id, text, updated_at FROM reviews ORDER BY updated_at DESC;
```

建议通过应用修改数据，避免手工编辑正在运行的数据库，导致同步版本号或引用不一致。`npm run backup` 可生成一致性在线备份。

## 餐后评价结构

以下仅为字段示例，并非真实使用记录：

```json
{
  "id": "review-uuid",
  "kitchenId": "home",
  "mealId": "home-1-1",
  "userId": "lin",
  "recipeId": "tomato",
  "recipeKey": "tomato",
  "text": "酸甜刚刚好，下次还想吃 😋",
  "createdAt": "2026-09-20T12:00:00.000Z",
  "updatedAt": "2026-09-20T12:00:00.000Z"
}
```

- 整餐评价的 `recipeId`、`recipeKey` 为 null；单菜评价保留本餐原菜谱版本 ID。
- `recipeKey` 对应菜谱的稳定 `reviewKey`，后续编辑菜谱时继承，因此新菜谱版本也能展示原有评价；上线前已经编辑过的旧版本暂不追溯合并。
- 每人对同一餐、同一评价对象保留一条记录，可编辑；只允许修改自己的记录。500 字符以内，允许只输入 emoji，不支持图片、评分或富文本。
- 有实际准备的菜品，且主厨标记完成或到达用餐结束时间后开放评价。按时结束的旧餐次即使未手动标记完成，也可以补评；取消餐次、空餐次、做菜份数为 0 的菜不可评价。
- 长期厨房成员可评价；临时成员需有本餐订单及未撤销的单餐授权，餐后只可回看与评价该餐，不能重新点菜或管理厨房。
- 主厨可在餐次入口查看反馈，单菜详情可查看同厨房该菜的历次评价。已有评价的餐次不可重置清空，请新建餐次。
- 保存失败保留输入；服务端事务与请求去重防止重复提交，编辑版本冲突提示载入最新评价。
- 兼容旧数据库：无 `reviews` 字段时按空数组读取，首次保存时写入，无需清空或重建历史数据。

入口：顶部爱心「评价」、已结束的「我的点菜 / 今日厨房」提示卡、菜谱详情中的「关于这道菜的喜欢」。

## 当前适用范围

拆表已经实施。保留 SQLite 是为了维持本机启动、离线使用和低运维成本；它支持事务与 WAL，但仍是单写入者。当前按实际轮询节奏与混合读写进行了千客户端测试，具体负载和边界以存储设计文档为准，不等于任意数量的并发写入保证。

身份仍由页面自由切换，读取仍是可信局域网的共享状态。公开上线时需要真实登录、服务端按成员身份过滤数据、分厨房同步及分页；进一步扩容可将已拆分的业务表迁入 PostgreSQL。这些不在本次保持前台功能的迁移中改变。
